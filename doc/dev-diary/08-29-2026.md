## [silkpurse](https://github.com/cmoid/silkpurse)

### Feedback from fellow implementors solicited

I just pushed a new [release v1.0.0](https://github.com/cmoid/silkpurse/releases/tag/v1.0.0) of Silkpurse. NOTE: This is a major change, hence the version bump. It now only works in what I call thin mode. There is no longer an embedded sbot server. To use it requires a running erlbutt node whose secret you own. It's intended to be a very lightweight thin client that can be used against different erlbutt nodes. It only keeps the sqlite index file locally so switching to run against other nodes is just a matter of changing a couple of env variables. I run one for development testing and also use it as a client for EarlButt.

I've also pushed an early release of [erlbutt](https://github.com/cmoid/erlbutt/releases/tag/v0.1.0) that this silkpurse can run against.

The main motivation for stripping sbot out is that erlbutt now supports archiving. Actually it's been there in EarlButt for a while now also, but disabled. Archiving has no impact on any pubs, clients, etc.. that replicate with erlbutt. But it is a major change and would require brain salad surgery on `ssb-db`, which is several versions behind in pathwork/bay/wonky/silkpurse, so I decided it was time to abandon sbot. It's amazing how much code [goes away](https://github.com/cmoid/silkpurse/blob/theseus/docs/theseus.md) 

I'll say more in the erlbutt section.

## [erlbutt](https://github.com/cmoid/erlbutt)

This first release of erlbutt, v0.1.0, is pretty stable. It still needs more testing but it has over 350 eunits now and 74 CT tests. It's been running as the EarlButt pub for a few weeks, though not really stressed yet. The reason I pushed this release out, along with a major release of silkpurse is that I want to solicit feedback from the other implementors, as well as butts in general, ghosts, lurkers, etc..

The support for archiving is in this release. Together with the next feature, *profile glimpses* (haven't settled on a name for these), I think they improve onboarding in a major way and put control of how far to replicate from in the user's hands. The idea of archiving is simple, and it might be flawed, but it looks usable to me. The key idea is that at any point a peer could choose to archive their history to date. It might be back to sequence 1 or just back to the last archive. A new post is created that points to a blob containing the archive. It turned out that this was a lot trickier than I thought, it took several iterations to get right, and I'm thankful to have Claude help with it. I had her write up a doc, [archive boundaries](https://github.com/cmoid/erlbutt/blob/main/doc/research/archive-boundaries.md), that discusses the feature in detail. I don't write well, even technical materials or math when I know exactly what I'm talking about. It takes me forever to coherently say what I mean to. I mention this solely because I know some folks don't want to touch AI. Everything in this doc is accurate and there are links at the bottom to all the appropriate code. I own it all, espeically the load-bearing pieces :)

Originaly I thought I'd write this up as a PR to the protocol guide, but I didn't want to waste anyone else's time if there is no interest. Archiving and support for multiple network ids is motivated by the use case I have in mind involving electronic health records. If there's no interest I'll keep compatibility but otherwise move along my own path.
